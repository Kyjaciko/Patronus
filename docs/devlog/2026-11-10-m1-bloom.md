# 2026-11-10: M1 bloom

*This entry closes the bloom item of milestone M1 in `docs/roadmap.md`. The
HDR target from ADR-0003 finally has something to feed: values far above
1.0 now spread into a glow before the tonemap compresses them. Claude
wrote the shader build rules, the benchmark analysis and the
documentation. The D3D12 and HLSL code is hand-written, as always.*

## The design

The full decision record is [ADR-0013](../adr/0013-bloom-mip-chain.md).
In short: a compute-shader mip chain at half resolution with 5 mips.
Five 13-tap downsamples come first; the first one also applies a Karis
average and a soft-knee threshold. Four 3×3 tent upsamples follow, each
added into the next larger mip. The tonemap pass then adds mip 0, divided
by the number of levels, to the scene before exposure. The reference is
Jimenez, *Next Generation Post Processing in Call of Duty: Advanced
Warfare* (SIGGRAPH 2014).

The first idea was to filter the scene texture in place, through one UAV,
in a single dispatch. That fails for three independent reasons:

- Thread groups in one dispatch are unordered, so a neighbourhood read
  races with the writes of neighbouring groups.
- The sharp image the composite needs is destroyed.
- A UAV cannot be sampled, so the bilinear taps the filter is built on
  are lost.

The resolution is a resource that holds several mips, with a separate view
for each one. A texture UAV always addresses exactly one mip (`MipSlice` is
a single number), so each mip gets its own UAV. Each mip also gets its own
SRV with `MipLevels = 1`, so a view never covers a subresource that is in
UAV state at the time. Pass i reads one subresource and writes another,
and barriers transition single subresources. Figures 1 to 3 in ADR-0013
show the views, the state of every mip per pass, and where the timestamps
sit.

## Four bugs worth remembering

**Ghost poles, only sometimes.** The upsample passed twice the destination
size as `dst_size`, while the dispatch covered the real size. Every
upsample therefore read only the top-left quarter of its source and
stretched it over the whole destination. The copy appears at twice the
distance from the top-left corner, so it was visible only when the poles
stood in that quadrant of the screen. That explained the "sometimes".
The first fix then set the tent radius to a quarter of a source texel. A
smaller texture has larger texels in UV, not smaller ones.

**A white screen with no message.** The debug layer breaks on errors
(ADR-0009), and without a debugger attached that shows up as a white
window. The message was recovered from the crash dump:
`EXECUTION ERROR #709: SET_ROOT_CONSTANT_INVALID … root signature, which
declares 3 root parameters`. The bloom constants for the tonemap pass (root
parameter 3) had been set with `SetComputeRoot32BitConstants`, which
targets the compute root signature that was still bound (the bloom one,
with three parameters).
Graphics and compute root signatures are separate bindings.

**A `bool` at the top of a constant block.** A C++ `bool` is 1 byte and an
HLSL `bool` is 4. Worse, HLSL does not let a vector cross a 16-byte
boundary, so the `uint2` after `bool` + `float2` moved from offset 12 to
offset 16 in the shader while C++ kept it at 12. Every field from there on
was read from the wrong place, in both the bloom passes and the tonemap.
The enable switch became a bit in the existing `flags` field, and vectors
now sit at offset 0 or 8 of each 16-byte register.

**A typed UAV load that is not guaranteed.** The upsample reads its own
texel back from an `R11G11B10_FLOAT` UAV. That works on the development
GPU, and it would be easy to believe that requiring feature level 12_2
covers it. It does not: `R11G11B10_FLOAT` is one of the formats whose
typed UAV loads are optional individually, at every feature level. This
is still open. ADR-0013 lists four ways out, and ADR-0009 now names
per-format capabilities as an exception to "assume, don't query".

## Measurement

Four timestamp zones were added: `bloom` around the whole chain, and
inside it `bloom down 0`, `bloom down rest` and `bloom up`. With bloom off,
the timestamps are still written, so each run has the same zones. Release,
1280x720, 1M particles, RX 7800 XT, first 1200 frames skipped:

| zone | p50 µs | p95 µs |
|---|---:|---:|
| bloom | 25.0 | 32.7 |
| bloom down 0 | 8.3 | 12.9 |
| bloom down rest | 6.0 | 8.5 |
| bloom up | 9.9 | 13.9 |

The prediction written down before the run was that `down0` would take
about 75% of the downsample time, because it reads three times the pixels
of all later levels together. It takes 58% (57% in Debug). The small
passes cost a near-constant 1.5 to 2.5 µs each whatever their size: mip 4
is 15 thread groups on a 60-CU GPU, and each barrier waits for the
previous dispatch to finish before starting one that cannot fill the GPU
again. `down0` moves about 4.6 MB in
8.3 µs, close to the card's DRAM bandwidth, so it is the one pass that
behaves as memory-bound. If time ever needs to be saved here, it is in the
small mips, not the large one.

The control-zone rule from M0 earned its keep again. In the Debug pair,
`render` moved 0.1 µs between the runs, so the 49 µs rise in `frame` is
real. 35 µs of it is inside the bloom zone, and about 14 µs falls outside
it. In this run every bloom barrier was inside the zone, so that remainder
is most likely the composite: one extra bilinear sample per pixel in the
tonemap. In the Release pair,
`render` moved 17.5 µs between the runs, more than the whole effect, so
the Release `frame` delta (−0.2%) says nothing. In Release, the zone itself
is the number to report.

## Parked deliberately

The order is implement, measure, then clean up. ADR-0013 lists the known
debt:

- the `/ 5` in the tonemap is tied to the mip count;
- the tonemap shares the bloom constant block, and its `dst_size` is
  overwritten each frame;
- the Karis bit is reset for the next frame instead of being set per
  dispatch.

Still open, with written predictions:

- the typed UAV load above;
- the 1440p run that tests the overhead explanation, where `down0` should
  grow about 4× and `down rest` less than 1.5×.
